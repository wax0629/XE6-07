# 提案：举报公开模型与基础处理

## 动机 / 用户故事

登录用户在浏览公开模型时，可能发现不适合公开的内容、授权问题、损坏文件或描述不符，需要向平台提交举报。审核员需要查看举报、记录处理结果，并在确认问题后使用已有下架能力处置模型。

共同需求是：建立一条私密、可追溯、不会因单次举报自动改变模型状态的基础举报处理流程。

## 目标用户

- 发现公开模型存在内容、授权或文件问题的登录用户
- 查看并处理举报的审核员
- 需要保护举报人身份和审核内容的社区服务

## 现有做法及不足

没有统一举报入口和处理记录时，用户只能通过外部渠道反馈，审核员无法获得结构化原因、对象和时间，也无法可靠追踪处理结果。若举报直接触发自动下架，又容易被滥用并影响正常模型。

## 前置能力

- 公共模型详情页能够稳定识别当前公开模型。
- 审核员具备查看模型和执行下架的受控能力。

## 本期范围

本期做：

- 在公开模型详情页提供举报入口。
- 举报原因包括不适合公开、版权或授权、文件损坏、描述不符和其他。
- 选择“其他”时必须填写说明。
- 提交前确认举报对象和原因。
- 举报成功后显示明确确认信息，但不自动下架模型。
- 同一用户对同一模型的未处理相同原因举报保持唯一。
- 已下架或不再公开的模型不能新增举报。
- 审核员查看待处理举报和完整详情。
- 审核员可以标记“已处理”或“无需处理”，后者必须填写说明。
- 审核员可以从举报进入模型下架流程；下架动作必须引用 `reportId`，并在下架成功后再完成举报处置。
- 保留举报记录和处理结果，并限制举报人身份和后台信息的访问。

本期明确不做：

- 不做自动下架、AI 内容审核和风险评分。
- 不做版权申诉和恢复上架。
- 不做证据附件上传。
- 不做举报人与作者之间的消息沟通。
- 不做账号处罚、封禁和信用体系。
- 不做批量处理。

## 关键决策与依据

### 备选方案

1. 举报达到条件后自动下架
   - 优点：处理速度快。
   - 缺点：容易被恶意或错误举报触发，缺少人工判断。
2. 举报只生成审核记录，由审核员决定是否处置
   - 优点：举报与模型状态解耦，处理过程可审计。
   - 缺点：需要审核队列和人工处理。
3. 全自由文本举报
   - 优点：表达灵活。
   - 缺点：难以去重、统计和分流。

### 本期选择

选择固定原因加可选说明，并由审核员人工处理；举报本身不改变模型公开状态。

原因：固定原因便于去重和查询，人工处理避免单次举报直接影响公共内容，同时保留必要的“其他”说明能力。

## 基本概念与信息结构

### 举报记录

- 举报模型、举报人、固定原因、补充说明和提交时间。
- 状态至少区分待处理、已处理和无需处理。
- 同一用户、模型、原因的未处理组合唯一。

### 处理结果

- 处理审核员、处理时间、结果和说明。
- 如需下架，通过受控的模型下架能力执行，不由举报记录直接修改模型状态。
- 下架处置使用 `pending -> action_pending -> resolved` 状态；下架失败时进入 `action_failed` 或退回 `pending`，不得标记为已处理。
- 下架操作记录 `reportId`，使举报决定、管理日志和模型状态变化可追溯到同一工作流。

## 原型 / 演示

模型详情页提供举报对话框，包含固定原因、其他说明和提交确认。

审核后台提供待处理列表、举报详情、已处理/无需处理操作，以及进入下架流程的入口。

## 验收标准

### 例子 1：提交固定原因举报

- 现状：用户无法结构化反馈公开模型文件损坏等问题。
- 提议后的行为：登录用户选择固定原因并确认提交。
- 验收：系统创建一条待处理举报并显示成功确认；模型保持公开，普通用户看不到举报正文和举报人。

### 例子 2：“其他”原因

- 现状：固定原因无法覆盖所有问题。
- 提议后的行为：用户选择“其他”时必须填写说明。
- 验收：说明为空时阻止提交并明确提示；填写后记录完整原因和说明。

### 例子 3：重复举报和网络重试

- 现状：重复点击可能生成多条相同待处理记录。
- 提议后的行为：同一用户、模型和原因的未处理举报保持幂等。
- 验收：重复请求只保留一条待处理记录，不显示多次成功造成的虚假计数。

### 例子 4：审核员处理举报

- 现状：举报缺少受控处理入口和历史。
- 提议后的行为：审核员查看详情后标记已处理或无需处理。
- 验收：处理结果记录审核员、时间和说明；“无需处理”缺少说明时不能提交，历史可查询。

### 例子 5：从举报进入下架

- 现状：确认问题后，举报记录与模型下架可能脱节。
- 提议后的行为：审核员进入受控下架流程，填写下架原因后再处理举报。
- 验收：只有下架操作成功后模型状态才改变；举报记录保留处理结果，普通用户无法访问后台信息。

### 例子 6：无权或不可举报状态

- 现状：未登录用户、非审核员或已下架模型可能绕过入口执行操作。
- 提议后的行为：未登录用户被引导登录；非审核员不能访问后台；已下架或非公开模型不能新增举报。
- 验收：所有拒绝均不创建记录、不泄露举报人或私有模型信息，并返回明确反馈。

### 例子 7：提交或处理失败

- 现状：失败请求可能显示虚假成功或丢失处理状态。
- 提议后的行为：系统保留原状态并提供重试。
- 验收：失败不创建或更新举报记录，页面明确显示失败，重试仍遵守幂等规则。

### 例子 8：从举报下架失败

- 现状：举报先标记已处理、后执行下架时，后一步失败会留下“已处理但模型仍公开”的矛盾记录。
- 提议后的行为：举报进入 `action_pending` 后执行带 `reportId` 的受控下架；只有下架成功才将举报标记 `resolved`。
- 验收：模拟下架服务失败时，模型继续公开，举报保持 `action_failed` 或待处理并记录失败原因，可由审核员重试；模拟成功时，模型下架记录、管理日志和举报处理结果均关联同一 `reportId`。
