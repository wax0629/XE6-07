# 提案：GLB 预览、可打印性检查与轻量修复管线

## 动机 / 用户故事

用户生成或上传模型后，需要先看到 GLB 的实际效果，再判断模型能否直接打印。当前缺少统一的 Web 预览、水密性与流形等可打印检查，也缺少对修复前后版本的追踪。

共同需求是：用户能够预览模型、运行可打印性检查、执行安全的轻量修复、复查结果，并随时回溯每次模型变更。

## 目标用户

- 生成或上传 3D 模型、准备继续打印流程的普通用户
- 需要定位网格问题并确认修复效果的创作者
- 需要读取模型版本和检查结果的后处理服务

## 现有做法及不足

模型生成或上传后，用户无法在统一页面确认 GLB 外观和基础复杂度，也无法知道水密性、流形、壁厚、自相交和法线是否满足后续打印要求。

模型在原始、修复、拓扑和分割等阶段会产生多个版本；如果没有不可覆盖的版本记录，可打印性检查报告、修复内容和当前模型之间容易失去对应关系。

## 本期范围

本期做：

- 在 Web 端加载 GLB，支持旋转、平移、缩放和重置视角。
- 展示顶点数、三角面数、水密性和流形状态。
- 高亮非流形边、孔洞和薄壁等问题区域。
- 检查水密性、流形、最小壁厚、自相交和法线一致性。
- 输出包含 pass/fail、问题列表和位置坐标的可打印性检查报告。
- 支持补洞、反转法线、去噪和简单加厚等轻量修复。
- 修复后自动复查，并提供修复前后对比。
- 允许用户确认或拒绝修复结果。
- 使用 `AssetRevision` 保存首次生成/上传和每次修复产生的版本。
- 本期落地版本数据结构和 API；版本切换 UI 后续补充。

本期明确不做：

- 不做复杂网格编辑。
- 不在轻量修复中执行大范围拓扑重建或复杂修复。
- 不做支撑生成和切片。

## 关键决策与依据

### 备选方案

1. 只提供预览和检查，不提供自动修复
   - 优点：实现和风险较小。
   - 缺点：用户发现问题后仍需离开平台处理，流程无法闭环。
2. 自动执行所有类型的网格修复
   - 优点：自动化程度高。
   - 缺点：复杂修复可能改变模型语义和几何，难以安全撤销。
3. 可打印性检查后只执行轻量修复，复杂问题进入独立后处理管线
   - 优点：覆盖常见问题，同时控制自动修改风险。
   - 缺点：复杂问题不能在本流程内一次解决。

### 本期选择

选择方案 3，并为每次修复创建新的 `AssetRevision`。

原因：轻量修复可以处理常见且边界明确的问题；不可覆盖的版本链同时支持回溯、差异预览和可打印性检查报告与模型版本的稳定绑定。

## 基本概念与信息结构

### AssetRevision

```text
AssetRevision {
  id
  modelId
  parentRevisionId
  snapshotURL
  auditReport
  changelog
  createdAt
  createdBy
}
```

- 首次生成或上传创建 `v1`。
- 每次修复创建新的子 revision，不覆盖父版本。
- `auditReport` 必须对应当前 revision 的快照。

### AuditReport

- `pass`: 总体是否通过。
- `issues`: 水密性、流形、壁厚、自相交和法线问题列表。
- 每个问题包含可用于查看器高亮的位置坐标。

## 原型 / 演示

处理页包含 GLB 查看器、模型基础信息、检查操作、问题列表和轻量修复入口。

修复完成后展示修复前后 side-by-side 或 overlay 对比、更新后的检查结果，以及“接受修复”和“拒绝修复”操作。

## 验收标准

### 例子 1：预览有效 GLB

- 现状：用户无法在处理页确认生成或上传模型的外观和复杂度。
- 提议后的行为：系统加载当前 GLB，并提供旋转、平移、缩放和重置视角。
- 验收：查看器流畅显示模型，页面展示顶点数、三角面数、水密性和流形状态，交互不会阻断页面其他信息。

### 例子 2：执行可打印性检查

- 现状：用户不知道模型是否存在孔洞、非流形边、薄壁、自相交或法线错误。
- 提议后的行为：系统对当前 revision 执行五类检查并生成结构化报告。
- 验收：点击“可打印性检查”后 30 秒内返回报告；报告包含 pass/fail、问题类型和位置坐标，查看器能高亮对应区域。

### 例子 3：执行轻量修复并复查

- 现状：常见孔洞、法线或薄壁问题只能离开平台处理。
- 提议后的行为：系统执行与问题类型对应的补洞、法线反转、去噪或简单加厚，并对结果重新检查。
- 验收：修复产生新的 revision 和 changelog；新报告明确显示原 fail 项是否转为 pass，父 revision 和原报告保持不变。

### 例子 4：确认或拒绝修复

- 现状：自动修复后用户无法比较变化或拒绝结果。
- 提议后的行为：系统展示修复前后对比，并等待用户确认。
- 验收：用户可以接受新 revision 或返回父 revision；拒绝修复不会覆盖旧版本或丢失检查记录。

### 例子 5：保持版本可追溯

- 现状：原始、修复和后处理模型之间缺少稳定关系。
- 提议后的行为：首次模型创建 `v1`，每次修复创建 `v2`、`v3` 等子版本。
- 验收：任意 revision 都能查询父版本、GLB 快照、对应可打印性检查报告、changelog、创建时间和创建者。

### 例子 6：无效或不支持的模型

- 现状：损坏文件或无法解析的模型可能让预览和检查处于不确定状态。
- 提议后的行为：系统停止进入可打印性检查和修复流程，并保留页面其他信息可用。
- 验收：页面显示明确错误和重试入口，不创建新的 revision，也不生成虚假的通过报告。
