# 提案：ComfyUI Job Capability

## 动机 / 用户故事

Hunyuan3D 多视图生成属于长耗时计算任务。外部系统如果使用同步请求等待结果，会遇到连接超时、状态丢失、重复提交和无法取消等问题。

共同需求是：把每次工作流执行抽象为可持久化、可查询、可取消和可审计的异步 Job，并向调用方提供稳定业务状态，隐藏内部节点执行细节。

## 目标用户

- 调用 Hunyuan3D 生成能力的业务 API 和外部系统
- 需要查看任务状态、失败原因和输出的用户界面
- 负责队列、Worker、资源调度和故障恢复的运行服务

## 现有做法及不足

同步请求会把长任务绑定到单次连接，调用方难以查询进度、恢复服务重启前的任务或安全重试。内部工作流事件直接暴露给外部，也会让调用方依赖 ComfyUI 节点和执行细节。

## 本期范围

本期做：

- 创建 Job 和稳定唯一标识。
- 定义 Job 生命周期和状态机。
- 支持请求幂等。
- 提供任务队列和 Worker 执行协调。
- 提供业务阶段、进度、查询、事件流或回调。
- 支持 queued 和 running 阶段取消。
- 支持任务超时和失败分类。
- 支持 Retry 和 Clone，并建立新旧 Job 关系。
- 持久化 Job，支持服务重启后的恢复或确定终态。
- 记录 Job 日志、指标和审计。
- 支持并发、优先级、配额和资源调度。
- 关联成功任务的所有约定输出。

本期明确不做：

- Job 不执行未发布或无效的生成能力。
- 已提交 Job 的参数不可原地修改。
- Job 成功不等于业务质量审核通过。
- 不向外暴露内部节点执行细节。
- 不返回服务器文件路径。
- 不负责模型训练和算法质量评价。

## 关键决策与依据

### 备选方案

1. 同步请求一直等待工作流结束
   - 优点：接口简单，调用方一次获得结果。
   - 缺点：长任务容易超时，不能稳定查询、取消、恢复或幂等重试。
2. 使用独立异步 Job，创建后立即返回 Job ID
   - 优点：任务生命周期可持久化，调用方可以查询、取消和恢复，内部执行可被稳定业务状态隔离。
   - 缺点：需要状态机、队列、Worker 和事件机制。

### 本期选择

选择方案 2。

原因：长耗时生成必须与单次 HTTP 连接解耦；统一 Job 也是幂等、取消、重试、资源调度和运行审计的基础。

## 基本概念与信息结构

### Job

- 稳定唯一标识。
- 已发布生成能力和不可变参数。
- 当前业务状态、业务阶段和进度。
- 创建、开始、结束和更新时间。
- 失败分类、是否可重试和约定输出。
- 幂等键、父 Job 和来源操作。

### Retry 与 Clone

- 都创建新的 Job，不修改原 Job。
- Retry 用于按规则重新执行失败任务。
- Clone 用于基于原任务参数创建新任务，可修改新任务参数。

### 执行事件

内部执行事件转换为稳定业务状态。外部调用方不需要理解节点名称、连线或服务器文件路径。

## 原型 / 演示

本期以 API 和任务状态为主，无独立视觉原型。消费端至少需要展示排队、运行、进度、成功、失败、取消中、已取消和超时等业务状态。

## 验收标准

### 例子 1：创建任务与幂等

- 现状：重复请求可能多次消耗生成资源。
- 提议后的行为：校验输入和参数后创建 Job，并立即返回稳定 Job ID。
- 验收：相同幂等键的重复请求不会创建第二个生成任务；调用方可以继续使用同一 Job ID 查询状态。

### 例子 2：排队、执行与进度查询

- 现状：调用方无法区分任务正在排队还是执行，也无法了解业务进度。
- 提议后的行为：Job 经队列进入 Worker，并把内部事件转换为统一状态、阶段和进度。
- 验收：调用方可以查询每次状态变化和业务进度；状态转换符合状态机，不暴露内部节点事件。

### 例子 3：取消任务

- 现状：长任务提交后无法停止，继续占用资源。
- 提议后的行为：queued 和 running Job 都可以请求取消。
- 验收：取消请求有明确最终结果；已终止 Job 不再产生新的约定输出，重复取消保持幂等。

### 例子 4：失败、Retry 与 Clone

- 现状：失败原因不清，修改参数可能覆盖原任务或丢失关系。
- 提议后的行为：失败 Job 记录分类和可重试性；Retry/Clone 创建新 Job。
- 验收：原 Job 保持不可变，新 Job 保存父子关系；不可重试失败不能被 Retry 绕过，Clone 可以使用新参数重新生成。

### 例子 5：超时和服务恢复

- 现状：服务重启或 Worker 中断后，已接受任务可能无记录丢失或永久停留在运行中。
- 提议后的行为：Job 持久化，并在恢复时继续执行或确定终态。
- 验收：服务重启后每个已接受 Job 都可查询；任务被恢复、标记失败、取消或超时，不存在无法解释的悬空状态。

### 例子 6：成功与约定输出

- 现状：任务显示成功但输出缺失，或直接暴露服务器文件路径。
- 提议后的行为：只有所有约定输出生成并关联后 Job 才成功。
- 验收：成功 Job 能查询完整输出引用，不包含服务器本地路径；成功状态不表示质量审核通过。

### 例子 7：并发、优先级、配额和资源调度

- 现状：多个任务可能无上限抢占 GPU，优先任务和用户配额无法生效。
- 提议后的行为：队列按已配置的并发、优先级、配额和可用资源调度。
- 验收：超过并发或配额的任务保持排队或被明确拒绝；高优先级按规则获得执行机会，调度结果可通过日志和指标审计。

### 例子 8：非法能力或参数

- 现状：无效能力和参数可能进入队列后才失败并浪费资源。
- 提议后的行为：系统在创建 Job 前完成能力和参数校验。
- 验收：未发布能力、无效参数或违反边界的请求不创建 Job，并返回稳定错误；已提交 Job 的参数不能原地修改。
