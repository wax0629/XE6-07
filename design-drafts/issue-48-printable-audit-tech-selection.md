# #48 可打印审计技术选型讨论稿

> 状态：设计草案，仅用于 PR 讨论，不合并。组内定稿后将结论回填到 #48。

## 背景与当前阶段

项目目前处于 MS1 空骨架阶段。#48 要求检查水密性、流形、最小壁厚、自相交和法线一致性，并返回可定位的问题区域，但本期不做自动修复、切片或工业级分析。

当前需要决定的是：现在直接锁定较完整的几何内核，还是先用简单方案验证需求和报告结构。

## 备选方案

| 方案 | 优点 | 缺点 / 风险 | 适合阶段 |
| --- | --- | --- | --- |
| `trimesh + PyMeshLab` | Python 接入快；`trimesh` 可完成水密、拓扑、法线和基础厚度分析，PyMeshLab 可补自相交定位；便于快速验证报告和高亮数据 | 两套网格数据结构之间要维护面 ID 映射；复杂自相交和薄壁结果需要验证；生产使用前需确认 PyMeshLab 相关许可证 | MS1 技术 POC |
| MeshLib | 单一 C++ 几何内核并提供 Python 绑定；支持自碰撞三角面查询、逐顶点厚度和后续修复能力；问题定位更容易保持一致 | 依赖和部署更重；官方目前为非商业免费、商业使用需授权；仍需用异常模型验证准确率 | MS2 候选正式内核 |
| CGAL + Embree | CGAL 的拓扑和相交判断可靠，Embree 适合高性能射线厚度计算；长期可控性强 | C++ 集成和自研胶水最多；壁厚规则仍需自行设计；CGAL 相关包存在 GPL / 商业授权要求 | 精度优先的长期方案 |
| Polygonica 等商业 SDK | 网格修复、厚度和大模型处理较成熟，有厂商支持，交付风险最低 | 授权成本、供应商绑定和采购周期明显；超出当前 MS1 骨架所需 | 明确商业化且预算充足时 |

- [MeshLib 文档](https://meshlib.io/documentation/index.html)
- [CGAL Polygon Mesh Processing](https://doc.cgal.org/latest/Polygon_mesh_processing/)

## 建议选择

建议采用“架构一步到位，算法分阶段验证”：

1. MS1 只固定稳定的审计接口和输出契约，包括状态、问题类型、严重程度、说明、面 ID / 空间位置和指标；具体几何引擎保持可替换。
2. 先用 `trimesh + PyMeshLab` 完成独立 POC，验证五类检查能否形成可读、可定位的报告，不把 POC 直接视为生产实现。
3. 同一批样本同时评估 MeshLib。进入 MS2 前，根据准确率、定位能力、性能、部署和许可证结果，在两者之间确定正式内核。
4. 只有当上述方案无法满足准确率或性能时，再升级到 CGAL + Embree；只有商业化和预算明确时，再评估 Polygonica。

这样可以避免在骨架阶段提前承担工业级方案的集成成本，也避免简单原型自然演变成无法替换的正式实现。

## 决策门槛

正式内核至少应通过以下同一组验证：

- 覆盖 #48 的五类检查，并能区分通过、警告和失败。
- 非流形、自相交和薄壁问题能返回稳定的面 ID 或空间位置。
- 对正常、拓扑损坏、自相交、薄壁和高面数模型建立不少于 30 个代表样本。
- 普通 MVP 模型在 30 秒内返回；超时可控且结果可复现。
- 重点比较漏报，而不只比较检测数量；阻断级问题不应被静默放过。
- 部署方式和许可证满足项目后续使用边界。
